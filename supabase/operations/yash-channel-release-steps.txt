   node scripts/ops/build-yash-channel-release.cjs prepare /absolute/path/prepare.sql
   Apply this postgres-only SQL after review. It creates temporary private deployment objects,
   not a cron or worker. Live dependency tokens and published heads stay unchanged.
2. In a bounded transaction:
   begin; set local statement_timeout='15s'; set local lock_timeout='500ms';
   select private.yash_channel_shadow_begin(); commit;
   Save batchId. It captures all currently valid published heads and requires one complete
   18-target cohort with 90 exact current/previous component windows.
3. First copy unchanged artifacts in bounded batches (at most 100 / 8 MiB each):
   begin; set local statement_timeout='15s'; set local lock_timeout='500ms';
   select private.yash_channel_shadow_copy('BATCH_UUID',100); commit;
   Repeat until remaining=0. This preserves original source timestamps/watermarks,
   payload bytes and upstream-completeness flags; it never claims a new source read.
   Then recompute one pending YASH item per separate bounded transaction:
   begin; set local statement_timeout='50s'; set local lock_timeout='500ms';
   select private.yash_channel_shadow_step('BATCH_UUID'); commit;
   This prepares one heavy item through frozen shadow functions and yields while a normal
   worker has an active lease. The old per-item copy path has been removed.
   Continue only after reviewing failures; no infinite retries. On timeout the current step
   rolls back and previously prepared items remain durable.
4. Before promotion, refresh the manifest in a short bounded transaction:
   select private.yash_channel_shadow_refresh('BATCH_UUID');
   Only changed job/head items lose their prepared payload. Restage the returned pending count.
   A changed roster/function/config dependency requires discard and a new reviewed batch:
   select private.yash_channel_shadow_discard('BATCH_UUID');
   Discard affects deployment staging only, never source or published data.
5. Build a single atomic promotion transaction:
   node scripts/ops/build-yash-channel-release.cjs promote /absolute/path/promote.sql BATCH_UUID
   Review/apply the WHOLE SQL transaction. Preflight acquires existing worker/dispatch/claim

   It then applies the classification migration and calls the existing normal completion

   Only repeated semantic checks share a postgres-only, same-transaction proof for the
   18 exact native targets. All per-item payload/provenance/scope/lease/fence/quota checks

   Quota, scope or dependency validation failure rolls back
   every function/head/job change. Existing workers are not paused or replaced.
   If heads changed, refresh/restage only changed items and retry the reviewed transaction.
   Repeated contention should be reported, not converted to an unbounded retry loop.

   with tokens as materialized(select target,private.provider_snapshot_dependency_token(target)token
     from private.provider_snapshot_targets where enabled)
