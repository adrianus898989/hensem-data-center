# EK7 / GEM7 / MAX7 订单明细采集 v5.6

基于用户提供的 v5.4 脚本修改。仓库版本的登录资料留空；用户下载包保留原文件顶部的配置。数据库连接、印度时区、三方字典、分页及金额检查沿用原代码。

## 当前优先做什么

先完整保存订单业务明细，并把查询直接融入现有三方量页面。保留原国家/团队页签、卡片和三方汇总表，不再交付独立查询大页面。

充值、提现分别写入现有 Supabase 的 `game66_charge_orders`、`game66_withdraw_orders` 明细表，GEM7/MAX7/EK7 按平台隔离。不从谷歌表格反推订单，也不新建收费项目。

现在增加保存 `uid`（会员 ID）及源接口提供的 `out_trade_no`（三方订单号），同时保留平台、订单 ID、订单号、三方名称/代码、业务方向、金额、状态、操作人和源时间。会员 ID 按文本原样保留，不截断前导0。源字段缺失留空、日志报告缺会员ID的笔数；不会把订单ID冒充会员ID。

额外业务字段按已确认的字段清单保存，登录密码、令牌、验证码、银行账号、手机号及IP不混入本次明细。原始明细表开启 RLS，匿名及普通登录角色均无直接读取权限；展示/搜索通过受模块、平台权限限制的查询接口，逐笔明细不返回原始敏感载荷。

同一平台、同一源订单 ID 重复抓取更新同一条订单，不重复累计。旧脚本丢弃的会员 ID 无法由汇总数恢复；从近期重新采到的订单开始补全，历史数据不清空、不自动全量重跑。

## 统计口径

| 查询 | 订单范围 | 成功金额、笔数 |
| --- | --- | --- |
| 创建时间 18 号 | 18 号创建的全部订单 | 仅这些订单中当前已经成功的部分；允许其在以后成功 |
| 成功时间 18 号 | 18 号成功的订单 | 包括当日创建及更早创建、18 号才成功的订单 |
| 成功时间 18 号 + 创建时间 1—17 号 | 1—17 号创建且18号成功 | 仅这些跨日成功订单 |

时间固定为印度后台时间（Asia/Kolkata，UTC+05:30），与运行电脑的时区无关。成功时间采用后台完成时间过滤参数 `update_time`。充值成功状态为 `1`，提现成功状态为 `3`；创建口径保留全部状态。

充值原始 `create_time/pay_time/update_time` 全部留在 `raw_payload`；统一查询的充值 `pay_time` 使用完成时间，提现用 `update_time`。金额和笔数分列；出款实际到账、提现手续费保持出款口径。成功时间筛选只包含成功订单，不把该集合的成功率误显示为100%。

## 替换和日常运行

在实际采集电脑上，Ctrl+C 停止旧脚本，备份旧文件后把下载的 `ek_sync.py` 放到 `~/Desktop/PY_CODE/ek_sync.py`。不要清除原来的 `PY_DATA/.gems7_sync_state`，旧未完成任务会继续保留。

```bash
cd ~/Desktop/PY_DATA
python3 -u ~/Desktop/PY_CODE/ek_sync.py --mode daily --platform all --lookback-days 1
```

`all` 表示 GEM7、MAX7、EK7。只跑 EK7 则用 `--platform EK7`。仍需要原来的 Chrome 9555 和 Supabase 配置。

每日印度时间00:15登记昨天的创建与成功任务；启动时也立即登记最近完整日。两种口径各自记录完成/失败状态，互不覆盖；失败项保留重试。成功日查询默认不限制创建日期，因此可发现以前月份创建、昨天成功的订单。重复采到的订单通过 `(platform_id,vendor_id)` 更新同一条记录，不重复累计。

## 只补18号成功时间（包含以前创建的订单）

先停止 daily，使用相同的 PY_DATA 目录运行：

```bash
cd ~/Desktop/PY_DATA
python3 -u ~/Desktop/PY_CODE/ek_sync.py --mode once --platform all --date 2026-09-18 --time-basis success
```

如果还要补18号创建的全部订单，删除 `--time-basis success`，默认会双采。补完后重新启动 daily。

指定成功时间段，以及可选创建下限：

```bash
python3 -u ~/Desktop/PY_CODE/ek_sync.py --mode once --platform EK7 \
  --time-basis success \
  --start 2026-09-18T00:00:00 --end 2026-09-18T23:59:59 \
  --created-since 2026-09-01
```

省略 `--created-since` 可包含更早月份的订单。时间段会按天拆为独立任务，首尾日保留所填小时。`--mode check` 只读源后台，不写入 Supabase。

```bash
python3 -u ~/Desktop/PY_CODE/ek_sync.py --mode status --platform all
```

日志区分 `created`（创建）和 `success`（成功），包含目标时间段、每页数量、写入确认、以前创建笔数；不能把已有数据库数据理解成源后台已全部同步。查看失败项后只补对应口径/日期即可。

## EK7 补 1—17 号

已经在跑这次补采的电脑无需重启。以下命令用于尚未启动的情况；不要与 daily 同时运行。

```bash
cd ~/Desktop/PY_DATA
python3 -u ~/Desktop/PY_CODE/ek_sync.py \
  --mode once --platform EK7 --data-type all --time-basis both \
  --start 2026-09-01T00:00:00 --end 2026-09-17T23:59:59
```

共 68 项（17天 × 充值/提现 × 创建/成功）。不加创建下限，成功口径包括更早创建的订单。重复执行整条 once 会重新读取这 68 项，不是只补漏；但入库会更新同一订单，不重复计数。失败项保留，恢复 daily 会继续处理待补项。

## 现有后台中的搜索与展示

入口：三方量/费率 → 香港盘口 → 时间口径选择“创建时间 · 订单明细”或“成功时间 · 订单明细” → 平台 EK7 → 查询。

- 时间精确到秒，使用印度后台时间，不随浏览电脑时区改变。
- 会员 ID、订单号/三方订单号精确匹配，保留前导零；三方、类型、业务方向可以组合筛选。
- 创建口径可选订单状态；成功口径固定成功订单。可筛选“只看跨日成功”，成功口径还可以展开独立的创建时间上下限。
- 卡片与原三方表保持；点击每行“查看”打开逐笔订单，包括会员 ID、两个订单号、三方、状态、金额、创建/成功/最近同步时间。
- 代收金额/笔数、代付金额/笔数只累计成功订单。实际到账/提现手续费只来自成功提现记录。
- 新增代付成功率：提现成功笔数 ÷ 创建提现总笔数；代收同理。汇总按合计笔数相除，不能平均各个平台百分比。
- 成功时间查询、单独状态筛选或仅跨日筛选不含完整分母，成功率显示“— / 不适用”，不能显示假100%。
- 旧日汇总没有完整提现分母时，代付成功率显示“待明细接入”。不使用金额计算成功率，也不把工单成功率冒充代付成功率。
- 页面标明实际应用的时间范围、最近同步和数据可能未补齐；查询失败保留上次结果及其原时间标签。

普通国家日汇总继续走原查询；只有日汇总的其他采集源没有可靠的小时数据，不能用日汇总冒充时间段统计。其他脚本逐个改为直接写 Supabase 后再切换对应模块；不清空原历史数据。

## 发布与验证

两份数据库迁移分别提供受限汇总和受限明细查询；查询函数不改变订单内容。第一份建立成功时间索引，已执行完成；本次第二份只更新查询函数，复用现有平台/时间索引，不在补采期间新建会员/订单号普通索引。后续索引优化应单独评估并发创建方案。

脚本自检、日期边界、重复任务行为、SQL权限/分页/状态、代收/代付汇总逻辑都有离线测试。前端构建和源码类型检查另行执行。采集电脑上的真实补采结果须待运行完成后，按相同条件对照源后台；不得把数据库已有笔数当成已全部采完。
