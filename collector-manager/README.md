# 本机 PY 运行管理器 · 首版

每台原来的 Mac 跑一个管理器，后台发出“运行 / 停止”，管理器每 15 秒读取一次指令，执行本机事先登记的 PY。每个任务仍使用原来的 Python 环境、工作目录、状态文件和浏览器。首版提供无业务的示例任务，部署后台后可以先验证它。

本目录的代码已可本地测试；生产接口、配置页面须部署后才能配对。这里没有自动安装开机服务，也没有登记或启动任何现有生产采集器。

## 现在先做：双击准备检查

把整个 `collector-manager` 文件夹解压到正在采集的那台 Mac 桌面，双击
`电脑准备检查.command`。它只显示 Python 环境、物理内存及 Python／Chrome
进程 RSS 汇总，不联网、不保存报告、不读浏览器凭据、不安装软件，也不会
启停原任务。RSS 合计可能重复计算共享页，不能当作实际独占内存或峰值。

如果 macOS 不允许双击，先不要修改系统安全设置；新开终端运行：

```sh
/bin/bash "$HOME/Desktop/collector-manager/电脑准备检查.command"
```

检查后把结果截图发来；Python 路径中的本机用户名可遮住。先不填写
`config.example.json`，也不运行 `pair`／`run`。后台上线后再按下一节接入。

## 第一次使用

1. 把整个 `collector-manager` 文件夹放到对应 Mac 上的固定目录。
2. 将 `config.example.json` 复制为自己的 `config.json`，填写实际后台 HTTPS 地址、该电脑的 Python 绝对路径、`demo_collector.py` 的绝对路径、它的工作目录。先只登记示例任务。
3. 在终端执行下面三步。示例中的 `/绝对路径/` 要换成实际路径；无需 `pip install`。

```sh
python3 /绝对路径/collector-manager/collector_manager.py check --config /绝对路径/collector-manager/config.json
python3 /绝对路径/collector-manager/collector_manager.py pair --config /绝对路径/collector-manager/config.json
python3 /绝对路径/collector-manager/collector_manager.py run --config /绝对路径/collector-manager/config.json
```

`pair` 时输入后台“添加电脑”生成的一次性配对码，输入不回显。设备长期凭据只保存到本机私有文件，不需要复制到聊天或 PY。每台电脑分别配对，不能复制另一台电脑的凭据目录。

保持管理器终端运行，在后台点击示例任务的“运行”，最多约一轮轮询后发出启动；再下一轮回传实际进程状态。首次登记默认停止。点击“停止”发送 SIGINT，等待 PY 自己退出。实际采集 PY 要先验证它收到 SIGINT 后的收尾行为，再开放生产停止按钮。

本机查看状态可另开终端：

```sh
python3 /绝对路径/collector-manager/collector_manager.py status --config /绝对路径/collector-manager/config.json
```

关掉管理器不会自动关闭它已经启动的任务；重新运行管理器会恢复管理，不能据此当作一键停止。电脑重启后，需要重新运行管理器，已恢复联网且后台仍要求运行的任务才会启动。无人值守登录启动应在试运行验收后单独配置。

## 接入第一份真实 PY

先核对它当前运行的完整命令，登记一个新的本地任务：

| 字段 | 填写内容 |
| --- | --- |
| `id` | 固定英文 ID，例如 `newar_finance`；不要随意改名 |
| `label` | 后台显示名称，不包含账号密码 |
| `python` | 原命令使用的解释器绝对路径；例如原虚拟环境里的 `bin/python` |
| `python_args` | 原来位于脚本名前的 Python 参数，例如 `["-B", "-u"]`；没有则省略 |
| `script` | 这份 PY 的原绝对路径 |
| `args` | 原启动参数拆成数组，例如 `["--mode", "daily", "--platform", "all"]` |
| `cwd` | 原来 `cd` 进入的目录，例如该机器自己的 `Desktop/PY_DATA` |

这一步只登记路径；源 PY、桌面报表、SQLite、待上传队列、浏览器配置都保留。原人工启动的同名脚本还在运行时显示 `external_running`，管理器拒绝再启动，也不会替你杀掉人工进程。必须先按原采集器的方式正常停止旧进程，再从后台运行。

修改本地任务清单后，重新启动管理器读取。已经运行的任务定义发生变化时显示 `config_invalid`，不会接管旧配置。首版不要热改正在运行任务的解释器、脚本、参数或工作目录；需要先停止并单独完成配置迁移。后台只管理已登记的任务，不能下发任意命令、路径或修改代码。

删除任务或修改任务 ID 前，必须先在后台停止并确认进程已退出。管理器会检查本机旧任务锁与守护进程；旧任务仍在运行、或无法联系但任务锁仍被占用时，新清单启动会被 `config_invalid` 拒绝，不向后台上报缺失清单，也不会结束旧进程。恢复原清单即可重新连接管理。确认已停止的旧任务可以移除，管理器仅退出空闲的守护进程。

## 状态和边界

- `running` 只证明进程还活着。成功入库、登录过期、完整回补尚未接入，不能根据这个状态判断数据已经采集成功。
- 断网、接口报错、配对凭据失效时保留已经运行的任务；不会按旧缓存命令启动新任务。后台显示离线不等于 PY 已经停止。
- PY 退出后，下一次成功轮询才按 30 / 60 / 120 / 240 / 300 秒退避重试；五次失败后阻止继续重启。修复原因后，在后台先停止，再运行以清除失败计数。
- 停止 20 秒仍未退出会显示 `stop_timeout`，不会自动 SIGKILL。需要查看原脚本当前操作；不得为了重开而删除进度文件。
- 独立任务守护进程持有任务锁。管理器重启能找回已启动的任务；如果守护进程异常结束但原 PY 尚在，显示 `orphaned_process` 并阻止重复启动。程序不会根据一个裸 PID 随意杀进程。
- 原 PY 主进程退出后，同一进程组中若还有辅助进程，或无法确认它们是否退出，也会显示 `orphaned_process` 并阻止重新启动。原组号在允许 PY 执行前写入本机私有记录，守护进程退出后仍能作只读排查；保存的组号绝不会直接用于发送终止信号。
- 浏览器登录、自动登录、断点回补、TG 报表迁移须逐份适配。当前管理器不改变任何原业务，不打开、关闭或调整 Chrome。
- 只登记持续运行的主进程。如果某份 PY 自行退出主进程、留下后台工作进程，需要先适配，不能按本版本通用启停直接接入。现有 `caffeinate` 等防休眠措施也需要另行保留。
- 本机状态默认存放于 `~/Library/Application Support/CollectorManager`，目录权限 0700，文件权限 0600。`device.json` 是设备凭据，不要上传。请保留该目录以恢复任务管理。
- 管理器事件只记录固定状态码，每个管理器 / 任务日志最多 3 个文件、每个 64 KiB。子进程控制台输出丢弃，不发送到服务器；原 PY 自己写的日志仍遵循原代码，需要后续逐份限制大小。
- 配置/API 的成功响应不会证明订单业务成功。首版也不降低浏览器的内存需求。

## 本地验收

```sh
python3 -B -m unittest discover -s /绝对路径/collector-manager -p 'test_manager.py' -v
```

测试只创建临时示例脚本和临时文件，模拟 API，不连接后台、不触碰现有采集器。需要本机允许读取进程列表；沙盒禁止 `ps` 时，重复进程安全检查会主动阻止启动。测试覆盖启停、重复点击、人工进程保护、断网、配对保密、管理器重启、任务锁、守护进程退出、失败退避以及日志大小。
