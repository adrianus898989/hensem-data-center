# 每日刷单分析

## 当前判定与范围

按平台当地日、同平台同会员 ID、全部三方及币种核对提交与成功记录。每日分析使用严格 `>` 门槛（10、15、20、30、50、100），默认超过 15 笔；当日成功、前日创建但当日成功，以及当日创建且后来已成功的订单都会排除该会员当日。多日分别判断，人数按平台 + 会员 ID 去重。

合格会员的无效笔数、金额及首末订单时间只统计当前所选三方、币种和精确半开时间范围。原成功率保持不变；剔除后成功率为成功笔数 /（创建笔数 − 无效笔数）。缺身份、状态、提交顺序或必要采集证据时不制造零或完整结论。

“连续高频提交 · 当天未充值”沿用独立的既有口径：每日至少 10 笔，以完成日判断当日是否有成功充值，分连续至少 3、5、10 天。它不代表历史从未充值，也不把不同平台的相同 ID 合并。

## 会员及逐笔明细

会员列表显示日期、会员 ID、会员 / 充值等级、充值次数、无效笔数、无效金额、首笔与末笔无效订单时间、涉及三方。源充值次数是源订单记录中的历史次数，不是当前窗口提交次数；同会员当日沿用既有聚合最大值。

点击无效笔数进入该会员当日的逐笔页：

- 金额分布按币种与数值金额分组，显示笔数和合计；覆盖全部符合条件的订单，不只当前分页。
- 逐笔列表按提交时间、订单号稳定排序，展示订单号、金额 / 币种、三方及源状态，分页大小最多 100。
- `memberOrders` 与父列表共用资格判断，必须携带会员 ID 和当地日，仍受平台、角色、三方、币种及时间范围限制。
- `events.detail` 与现有明细权限在宿主桥及数据库角色网关同时执行；返回会员列表保留原筛选和分页。
- 源缺失金额和历史充值次数保留未知，明确的 0 显示 0。时间使用平台时区。

## 来源与会员属性采集

支持 AR、新 AR、LG、GAME66；YASH 精确匹配原生 `kb / IN / YASH.BET` 身份，读取 `private.yash_orders`，不放开其它 KB 来源。

YASH 的 UID、原始订单号、提交 / 完成时间、状态、三方及原生金额已有独立采集链路。每日和连续日统计核验 `createTime` 与 `completeTime` 两条流：完整回执、源 / 上传 / 入库计数一致、当前表计数复核、整日范围无缺口。缺少回执的历史日不能当作零；主指标为不完整，已观察部分仍保留。YASH 未提供等级和历史次数时保持未知，不从首单标记推断。

2026-10-10 生产核对确认 JALWA 走旧 AR，旧订单表未保存 `member_level` 与 `recharge_count`，原采集上传也裁剪为固定字段。源站能显示这两列并不意味着数据库已有数据。接收接口与存储已兼容可选等级、次数，旧客户端仍可上传，已有事实不会被缺失字段覆盖。生产最近 200 笔 JALWA 充值订单及关联快照未存两项；这不能证明采集本地没有抓到。还需核对实际运行文件是否已上传字段，并补传已有源记录或重采相关历史日期。通道采集脚本 `ar_channel_sync_9222.py` 不负责订单或会员属性。

新 AR 按已确认的 `rechargeLevel` / `rechargeCount` 字段保存，旧历史仍需重采。L0 可能同时有成功充值和非零历史次数，不能把等级直接当作“从未充值”，也不能拿 VIP、是否首充或窗口内订单数代替。

## 验证

离线 PostgreSQL 测试覆盖整日跨三方资格、跨日成功、精确时间范围、分布与分页对账、零及未知金额、时区、越权与输入拒绝、数据库函数 ACL / 配置保持；UI 测试覆盖返回、分页、旧响应取消和未知值。数据库迁移对已审定函数定义做漂移检查，并验证幂等重放。
